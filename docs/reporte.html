1. Resumen ejecutivo

Se construyó un sistema observable de nivel producción sobre Google Cloud (GKE + Cloud SQL) con tres microservicios encadenados (service-a → service-b → data-service) instrumentados con OpenTelemetry en los tres pilares (trazas, métricas y logs correlacionados por trace_id). Sobre esa base se implementó detección de anomalías con umbrales dinámicos (baseline + 2σ), una regla de correlación errores+latencia con enriquecimiento por trace_id, observabilidad de red (VPC Flow Logs, Dataplane V2/eBPF) y seguridad (escaneo de CVEs), y se validó la resiliencia con experimentos de caos controlados midiendo el MTTD y el consumo de error budget.

Decisión de alcance: la solución se desplegó en una sola nube (GCP). Se priorizó la profundidad (AIOps, caos medido, SLOs) sobre duplicar la infraestructura en AWS, por costo y por la recomendación de ejecutar en un sandbox aislado. La extensión a AWS (RDS, ECS Service Connect, Security Hub) y el service mesh quedan como primeras iniciativas del roadmap (sección 9).

3. Módulo A — Arquitectura observable completa

3.1 Tres pilares correlacionados

  • Trazas: FastAPIInstrumentor.instrument_app (span servidor por request), HTTPXClientInstrumentor (propagación W3C entre servicios) y spans de negocio. Resultado: una sola traza atraviesa los tres servicios.
  • Métricas: semconv HTTP estable (http.server.request.duration con http.response.status_code) habilitada con OTEL_SEMCONV_STABILITY_OPT_IN=http; son la base de los SLIs. Además db.client.operation.duration en data-service.
  • Logs: JSON estructurado con trace_id y span_id inyectados por un formatter, lo que permite saltar de un log a la traza.

3.2 Database spans con OTel DB Semantic Conventions (estables)

db.system.name            = postgresql
db.namespace              = appdb
db.collection.name        = products
db.operation.name         = SELECT
db.query.summary          = SELECT products        (nombre del span)
db.query.text             = SELECT sku, name, category, price FROM products WHERE sku = %s
server.address            = 10.35.128.3            (IP privada de Cloud SQL)
server.port               = 5432
db.response.returned_rows = 1

La query se registra parametrizada (%s), por lo que nunca contiene datos del usuario. Se descartó Psycopg2Instrumentor en data-service porque emite los atributos legacy (db.statement, db.name) y duplicaba el span.

3.3 Service mesh

No se implementó en esta entrega. En una sola nube el mesh no cambia la cobertura de los requisitos, y su integración con Chaos Mesh (sidecars Istio + inyección tc) añadía riesgo. La visibilidad L7 entre servicios se obtiene hoy de las trazas OTel (grafo de dependencias de Jaeger). Se incluye en el roadmap (Cloud Service Mesh, mes 2).

4. Módulo B — AIOps: detección automática de anomalías

4.1 Umbral dinámico baseline + 2σ

svc:error_ratio:rate1m          = 5xx / total  por servicio (ventana 1m)
svc:error_ratio:baseline_avg30m = avg_over_time(svc:error_ratio:rate1m[30m])
svc:error_ratio:baseline_stddev30m = stddev_over_time(svc:error_ratio:rate1m[30m])

ALERT ErrorRateAnomaly2Sigma
  svc:error_ratio:rate1m > baseline_avg30m + 2 * baseline_stddev30m
  and svc:error_ratio:rate1m > 0.01        # piso: evita alertar cuando el baseline ≈ 0
  for: 30s

4.2 Regla de correlación del enunciado

ALERT AIOpsCorrelatedAnomaly
  (error_rate > baseline + 2σ  and  error_rate > 1%)
  and on (exported_job)  latency_p99 > 0.5s (SLO)
  for: 30s   →  severity=critical, page=true

Enriquecimiento con trace_id: una métrica agregada no contiene el trace_id. Cuando la alerta pasa a FIRING, el orquestador (scripts/run_chaos.py) consulta la API de Jaeger por la traza más reciente con error=true del servicio afectado y adjunta su trace_id a la alerta. Así quien responde pasa de "subió el error rate" a la traza exacta del request fallido.

6. Módulo D — Chaos Engineering controlado

SLOs: disponibilidad del borde (service-a) 99,5% en 30 días; latencia p99 < 500 ms (baseline medido ≈ 400 ms). Con 2 req/s el error budget mensual es 0,5% × 2 × 86.400 × 30 = 25.920 requests fallidos. Carga constante de 2 req/s con k6 (k6/carga-constante.js) y sandbox dedicado (namespace otel-lab en un clúster propio).

Log completo del orquestador en docs/evidencias/chaos/resultados-exp1.txt y resultados-exp23.txt.

Análisis del experimento 3 (la alerta correlacionada no se disparó): con ambos faults activos el p99 del borde subió a ~2,5 s y hubo 64 respuestas 5xx, pero AIOpsCorrelatedAnomaly no pasó a FIRING. Causa: el baseline de 30 min incluía los errores del experimento 2, lo que elevó la media y la desviación estándar; el umbral baseline + 2σ quedó por encima del error rate del experimento 3 (contaminación del baseline). Sí alertó LatencySLOBreach (SLO de latencia violado), por lo que el incidente no pasó desapercibido. Mitigaciones: (1) excluir del baseline las ventanas con caos o incidentes (etiqueta de mantenimiento), (2) baseline más largo (24 h–7 d) con estacionalidad, (3) espaciar experimentos ≥ la ventana del baseline, (4) combinar 2σ con un umbral absoluto ligado al burn rate del SLO.

Nota metodológica: el MTTD se mide desde el instante en que se envía el fault (T0) hasta que Prometheus marca la alerta FIRING; incluye la ventana de rate (1 m), la evaluación (15 s) y el for: 30s. En el experimento 2 el T0 incluye el rollout de los pods, por lo que el valor es conservador. Se usó inyección controlada por variable de entorno porque HTTPChaos de Chaos Mesh no admite un porcentaje de requests (abortaría el 100%).

10. Reproducibilidad

cd terraform/gcp && terraform init && terraform apply     # infraestructura (~15 min)
./scripts/deploy.sh images && ./scripts/deploy.sh app && ./scripts/deploy.sh chaos-mesh
k6 run -e HOST=<IP> k6/carga-constante.js &
python3 scripts/run_chaos.py                               # experimentos + MTTD + ruido
terraform destroy                                         # limpieza del sandbox
